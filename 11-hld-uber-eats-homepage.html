§ 01
Clarify Requirements
Open with this — don't assume anything yet

The Bar Raiser is watching whether you control scope before drawing boxes. Clarifying isn't politeness — it's buying yourself the right to simplify later. Ask 2–3 targeted questions, reflect back what you heard, then move on.

Open the session with this
"Before I draw anything, I want to align on three things: what's actually in the homepage, how hard eligibility is versus ranking, and what p99 needs to feel like — because those three decisions control almost everything else I'm going to design. Can we go through those quickly?"

The 6 questions that matter

Homepage scope "When you say homepage — are we doing the full experience: nearby restaurants, reorder strip, cuisine chips, promos, maybe sponsored slots? Or narrower?" Changes whether you need a mixer, a feature store, sponsored ranking
Freshness on browse "For the restaurant list itself — not checkout — is it okay if trending or popularity is a few seconds or minutes stale? Or does the product need it basically real-time?" Drives how aggressively you can cache, which changes your whole architecture

Don't ask more than 3 questions in a row without pausing for their input. This should feel like a conversation, not an interrogation.
§ 02
Functional & Non-Functional Requirements
Lock these explicitly — everything else is derived from here

Don't just list features. Walk through FRs as "what we're building" and NFRs as "how it has to behave." This shows you understand the difference between product correctness and engineering constraints.

Functional Requirements

Say this out loud — ~60 seconds
"Based on what we aligned on — here's what we're actually building. The homepage needs to: resolve where the user is, then show only restaurants that are actually serviceable for that location. The response is a structured page — sections like reorder, near you, promos, cuisine chips — each with a type, title, items. Each restaurant card carries enough to make a decision: name, hero image, rating, ETA, delivery fee, open or closed, and an id to hand off to the detail page. Events like impressions are async — they're not on the critical read path."
Core: Location + Eligibility
Resolve lat/lng or saved address → only show restaurants that are in-zone, not hard-closed, not paused. This is a trust boundary, not a ranking preference.
Core: Homepage Shape
Structured sections (reorder strip, near you, promos, cuisine chips). Each section has a type, title, cursor/pagination, and items. Cards have enough data to decide to tap.
Core: Async Events
Impressions and clicks are emitted asynchronously — for analytics and ranking feedback. They never block the homepage response.
Out of Scope
Checkout, payment, driver dispatch, text search (delegated). Mention these explicitly so you control the boundary.

Non-Functional Requirements

The key NFR line
"I want to be explicit about tiered consistency. Hard eligibility — is this restaurant actually in my zone, is it open — that has to be correct. Ranking order, trending scores, cached ETAs? Those can be eventually consistent with an explicit staleness budget. Browse can be a little stale. 'You can order here' cannot be a lie."

"We never show a restaurant as orderable if it fails hard eligibility. Ranking may degrade. Eligibility cannot lie."

Consistency Model

Strong Consistency Required
Is this restaurant in my delivery zone? Is it open right now? This is a trust question — wrong answer breaks the user's ability to order. Must be correct.
Eventually Consistent (explicit SLO)
Ranking order, trending scores, cached ETAs, popularity signals. Can be seconds to minutes stale. Browse can tolerate this — ordering cannot.

Commit Boundary

Say this clearly — it shows systems thinking
"The homepage response commits when eligibility filtering is complete — that's a hard guarantee — and ranking is either done or we've hit the deadline and fallen back to a simpler ordering like distance or popularity. The user always gets a real response. It might not be the most personalized order, but it's always correct about serviceability."

Evolution — Phase It Honestly

V1
MVP — Ship and Learn
Single metro. Geo filter + simple rank (distance + rating). Aggressive caching with honest staleness labels. Strict in-zone eligibility. This builds trust and shows what traffic actually looks like.
V2
Growth — Add Intelligence
Feature-based ranking, reorder rail, personalization, stream aggregates for trending. Handle hot cells. Add partial degradation per section. But only when V1 metrics tell us we need it.
V3
Scale — Multi-Region + ML
Multi-region reads, dense-city sub-cell tuning, ML-based scoring, experiments framework. Pay for this complexity only when product and metrics prove it's worth it.

High-Level Architecture
Walk it like a pipeline — then pause and ask where to go deeper
Narrate the diagram — don't just list boxes
"Think of this as a read funnel. Client hits CDN for images, gateway for auth and rate limiting, then a homepage service that's basically: locate → geo candidates → filter → rank → assemble. § 07
Deep Dive: GET /home End-to-End
This is where Bar Raiser time lives — ~20 min

Walk through the request like a debugger. Each step should answer: what does this component do, what can go wrong, and how do I handle it?

Set up the deep dive
"Let me walk GET /home end-to-end. I'll narrate the critical path first, then the main optimizations. The default path: cap geo → hydrate batch → two-stage rank with deadline → assemble. The first optimization is almost always the candidate cap and single-flight on hot cells — not a cleverer model."

Step-by-step pipeline

Step 1 — Auth at Gateway + Location Resolution ▼

What happens: Auth token validated at the gateway (not inside the homepage service). Location is resolved from GPS, saved address, or fallback to coarse/IP location.

Say unprompted: "We log which source was used — GPS, saved address, IP fallback — because half the weird tickets in prod are location quality issues, not service bugs."

Edge case: GPS is noisy or missing → prefer saved address first, fall back to coarse with product-level disclosure if required.

Step 2 — Geo Candidates (Spatial Index) ▼

What happens: Query spatial index using H3 or geohash — query the cell the user is in plus adjacent neighbors. Cap the result at N candidates (say, 200–500).

Why neighbors? A restaurant just across a geohash cell boundary would disappear without this. This fixes the classic boundary miss bug.

Dense areas: In central Amsterdam, hundreds of restaurants might be in one cell. Sub-partition or enforce a strict cap — otherwise ranking blows your p99.

Say unprompted: "Cell plus neighbors avoids boundary misses. We cap candidates in dense areas — otherwise we'd score 800 restaurants per request and p99 becomes meaningless."

Step 3 — Hard Eligibility Filter (STRICT) ▼

What happens: Filter the candidate set: not hard-closed, in delivery zone, not paused, passes any compliance flags. This is a yes/no pass.

This never degrades. Even if ranking is down, even if we're under extreme load — eligibility filtering stays correct. A restaurant fails eligibility, it's not on the page. Full stop.

Quick win: Pre-compute an "open now" bitmap or next_open_at for each restaurant. Filter out obviously closed ones before they ever hit the expensive ranking step.

Step 4 — Batch Hydration (Catalog) ▼

What happens: Fetch card fields for all eligible candidates — name, images, rating, fee rules, tags — in one batch call, not N individual lookups.

Say unprompted: "Batch fetch to avoid N+1. If we fire one DB call per restaurant on a list of 200, that's a 200-call fan-out on the hot path — instant p99 problem."

Cache: Restaurant metadata is a great Redis candidate — it changes infrequently. Short TTL + event-driven invalidation on merchant edits.

Step 5 — Two-Stage Ranking (Time-Boxed) ▼

Stage 1 — Wide retrieve: Score all eligible candidates cheaply — distance, rating, basic popularity. Keep top-K' (say, 50).

Stage 2 — Re-rank: Apply richer scoring (CTR history, user affinity, business rules) to just the top-K' set. This is where personalization plugs in if in scope.

Deadline: Ranking has a hard time budget — say 80–150ms. If it times out, fall back to distance + popularity ordering. Eligibility still holds — we just serve a simpler order.

Say unprompted: "Two-stage retrieve-and-rerank lets me control latency. I score cheap on the wide set, expensive only on the short list. And ranking is always time-boxed — on timeout, fallback order, not a blank page."

Step 6 — Assembly + Response ▼

What happens: Assembler builds the page sections. Mixer injects promo slots and experiment variants without polluting core rank invariants. Sets ETag for conditional GETs.

CDN: Images are served from CDN, not the API response. The response payload is JSON only.

ETag: If the ranked list hasn't changed (same restaurant set, same order), return a 304 Not Modified. Saves bandwidth on frequent refreshes.

Experiment slots: If an A/B test needs to inject a sponsored restaurant at position 3, that goes through the mixer — not directly into the ranker — so we can audit and rollback without touching core logic.

Production War Story — Say This If Asked About Incidents
"The classic prod incident here is a cache stampede: a hot cell's Redis key expires, 500 concurrent requests all miss at once, and you hammer the DB. The fix is single-flight (only one request refills the cache, others wait) plus TTL jitter (randomize expiry by ±10–20% so keys don't all expire simultaneously). Also warm critical keys on deploy."
§ 08
Scaling & Bottlenecks
Name what breaks first — then the fix sounds obvious
Frame the bottleneck discussion
"If we 10x traffic, the shape stays the same — I just get more aggressive on caps, caching, and rank deadlines. The eligibility rules don't change, we just apply them cheaper. The three bottlenecks I'd monitor first are: hot geocells, rank tail latency, and cache stampede."
🔥 Hot Geocell
Dense city center — a single geohash cell has 500+ restaurants. Every request queries the same shard → tail latency, shard overload.
Fix: sub-partition cell, read replicas, enforce strict candidate cap, backoff on shard overload
⏱ Ranker p99 Tail
Ranking is the most expensive step. Under load or model complexity, p99 blows the budget and drags the whole response.
Fix: hard time-box on ranker, circuit breaker, fallback to distance/popularity ordering
💥 Cache Stampede
Popular cell TTL expires. All concurrent requests miss cache simultaneously. DB gets hammered. p99 spikes.
Fix: single-flight (only one refills), TTL jitter (±10–20%), proactive warming on deploy
📍 Bad GPS / Location
Noisy or incorrect GPS puts user in wrong cell → shows wrong restaurants → trust broken.
Fix: prefer saved address, log location source, UX disclosure for coarse fallback
🌡 Cold Cache on Deploy
New deployment clears Redis. First requests after deploy hammer the DB until cache warms up.
Fix: warm critical cell keys during deploy, gradual rollout / blue-green deployment
📋 Stale Menu / Price
User sees "£10" on homepage, gets to menu and it's £12. Creates support tickets and erodes trust.
Fix: version keys on card payload, short TTL on price fields, event-driven invalidation on merchant edits

Degrade the fancy stuff before you degrade truth

"My priority order when something degrades: shed personalization rails first, then promos, then trending. Never shed eligibility correctness or the core 'near you' list. Ranking down does not mean empty page — it means fallback ordering. Users can still order."

Retry policy — get this right
"Retry only idempotent reads, with exponential backoff and jitter. Never retry on timeout — that doubles your load. Circuit breaker trips after N failures in a window, then probes with a fraction of traffic. Bulkhead means one slow dependency can't exhaust all worker threads."

§ 11
Bar Raiser Follow-Ups & 60s Close
2–4 sentences each, then stop and let them steer

Common Bar Raiser probes — how to answer

"How do you handle new restaurants being cold-started? They have no CTR history." Ranking depth
Cold-start is a classic explore-exploit problem. I'd reserve a small number of exploration slots — say 5% — where new restaurants are shown regardless of history, then we measure their actual CTR. For scoring, fall back to category-level or city-level priors until we have enough signal. I'd also watch impression share by restaurant tenure on a dashboard — if new restaurants never get surfaced, that's a product and fairness problem, not just a ranking one.
"What happens if we need to expand to multi-region — say Amsterdam and London on the same stack?" Scale / global
Catalog and spatial data are partitioned by region from the start — each region gets its own shard/instance. User reads hit their local region. Analytics and order aggregates are eventually consistent globally — that's fine, we don't need real-time global rollups for the homepage. The main thing I'd add is a regional config layer so business rules (zones, compliance) are applied locally without crossing regions.
"What's the difference between your search index and your geo nearby index?" Data model
Different access patterns, different indexes. The nearby index is purely spatial — cell → restaurant IDs, fast lookup, Redis-friendly. The search index is text + facets + geo filter, built in OpenSearch or similar — it powers "sushi near me" queries with relevance scoring. They share the same restaurant ID as a key, and you join in the BFF layer if you need both. I wouldn't try to do text search in the geo index or vice versa.
"How do you prevent a bad deploy from breaking the homepage for everyone at once?" Operational safety
Feature flags are the main tool — I can toggle ranking changes, new sections, or experiment slots without redeploying. For ranking specifically, I'd dark-launch first: run the new ranker in shadow alongside the current one, compare output, then gradually shift traffic. Cache versioning means old and new cached data coexist during rollout. And I'd set an error budget SLO alert so if the fallback rate spikes above N%, we pause the rollout automatically.
"Your design shows ranking in the hot path. What if the ML model takes 500ms? Isn't that a problem?" Ranking vs latency
Yes, that's exactly why ranking is time-boxed. If the model exceeds its budget — say 150ms — we cut it off and serve whatever partial result we have, or fall back to distance + popularity. The user gets a correctly eligible list in a sensible fallback order. If 500ms becomes the norm, that's a signal to precompute more of the ranking offline and do lighter online blending. I'd track "ranking fallback rate" as a first-class SLI — if it's above 5%, we have a problem to fix.
"Walk me through a user opening the app right as a restaurant is closing." Race condition / edge case
Classic race condition. The restaurant appears on homepage based on cached state that says it's open. User taps through — at menu load or cart add, we do a stricter read of current status and block ordering if it's now closed. The homepage can be slightly stale; the order placement path must be fresh. We also have a short TTL on open/closed status in the cache — say 60s — plus event-driven invalidation when a merchant toggles their state. And we expose "opens at" on the card so users understand the situation.

End with this — confident, no new ideas
"To summarize what we built: a read funnel — geo candidates capped with neighbor cells, batch hydration to avoid N+1, two-stage ranking under a hard deadline with fallback ordering, aggressive caching where staleness is acceptable. Orders stay ACID in SQL. Metrics are defined from the warehouse, not from cache. And the one invariant I held throughout: eligibility stays correct even when ranking degrades. If you were to push me on one thing to evolve first, it'd be precomputing more of the ranking offline — once we have the traffic data to prove it's worth the pipeline complexity."
